対象機: MacBook Pro M4 Max 40C GPU / 128GB / macOS 26.x。構成は llama-swap → mlx-serve (Qwen3.8-Flash-Next の 2 パック)。
調査はクラウドサンドボックスで行い、本機では何も実測していない。数値は出典付きの他者実測か公式値で、当機向けの値には「推定」「未実測」と付けた。

## (a) TL;DR

- **モデル: 据え置き**
- **mlx-serve: 導入済み 26.11.2 / 最新リリース 26.11.3 (11-19) → 26.11.3 へ更新推奨。**
  - 前回「main に積まれている (未リリース)」とした preflight の判定式変更 (#1147、macOS が空けられる RAM を空きに数える) と、qwen4_exp の層ごとロード・GPU タイムアウトの再試行が入った。Lightroom / Docker 常駐時の起動拒否 (11-03〜04) の対策になる見込み。
  - キャンセル時の SIGSEGV 修正 (#1163)、キャンセルされた prefill の prefix cache 保持 (#1170)、Metal の GPU 作業拒否の検出なども入っている。
  - 26.11.4 はプレリリース (`v26.11.4-pre-release.1`、11-21) のみ。Inkling 2 Mini 対応と `--os-reserve-gib` の修正が中身で、当機の運用には効かない。
  - sha256 は Formula 掲載値と、tarball を実際に取得して計算した値が一致した (`a45db31a…`)。tarball の構成も従来と同じ。
- **llama-swap: 導入済み v270 / 最新 v275 → 更新推奨 (低優先)。** 理由: v272 で、1MiB を超えるボディのとき上流のエラーが 200 になる不具合が直った (#1319)。v274 では、ボディを持つ POST だけにフィルタを掛けるよう修正された (#1354)。config の互換性を壊す変更は無い。

**前回までの記述の訂正:** 正本・config.yaml・前回レポートは「prefill 中は他の全リクエストが 1 トークンも進まない」(2026-09-06 調査) としている。しかし mlx-serve には **26.11.1 から `--prefill-decode-share` (既定 0.25) がある**。他のリクエストの prefill 中も、decode 中のストリームが壁時計時間の 25% を確保する仕組みで、ソースを読む限り qwen4_exp にも効く。
- 一方で、新しく来た短いリクエストを prefill のチャンク境目に割り込ませる機能 (26.11.3 の `X-MLX-Priority` を含む) は、**qwen4_exp を対象外にしている** (コードで確認)。
- 現行版で並列挙動を測り直すことを推奨する → (e)-3。

### 既知の弱点の追跡

**prefill 中に他のリクエストが止まる問題**
- 26.11.1 以降、`--prefill-decode-share` (既定 0.25) がある。docs/cli.md の説明は「decoding streams keep this wall-time fraction during another request's prefill; the prefill runs 1024-token chunks meanwhile」。
- qwen4_exp は whole-prompt prefill ではなくチャンクループで prefill し、`batches_decode = true` なので、**decode 中のストリームは止まらなくなっている可能性が高い** (コードから推定、未実測)。
- gotcha 文書には「誰かが decode している間は prefill 幅を 2048 に狭める (`companyPrefillChunk`)」とある。
- 一方、**新しく来たリクエストの prefill は、境目での割り込みの対象外** (qwen4_exp はモジュール状態を持つため) なので、長い prefill の後ろで待つ。2026-09-06 の「77k prefill 中の短文が初トークンまで 127 秒」という症状は、新規リクエストについては残っている見込み。

**プロセスを跨ぐスワップ直後の preflight**: 26.11.3 でも解放待ちは入っていない。`settle` を維持する。

### 3. 並列挙動の再測定と、config.yaml のコメント修正 (更新後、任意)

26.11.3 に上げたあと、2026-09-06 と同じ手順で次を測る。
- 長文 prefill (例: 77k) 中に、既に decode 中のストリームが進むか
- 新規の短文リクエストの初トークンまでの時間

結果によっては、config.yaml 冒頭の「prefill 中は他の全リクエストが 1 トークンも進まない」「チャンク境目で decode を挟まない」という記述を直す。案:

```diff
-#   mlx-serve は decode は並列に束ねられるが、prefill 中は他の全リクエストが 1 トークンも進まない
+#   mlx-serve は decode は並列に束ねられる。26.11.1 から --prefill-decode-share (既定 0.25) で、他の prefill 中も
+#   decode 中のストリームは壁時計の約 25% を得る (要実測)。ただし新規リクエストの prefill は、qwen4_exp では
+#   長い prefill の境目に割り込めず後ろで待つ (X-MLX-Priority も qwen4_exp 対象外、26.11.3 で確認)。
+#   以下は 2026-09-06 (26.9.x) の記録: prefill 中は他の全リクエストが 1 トークンも進まなかった
```
