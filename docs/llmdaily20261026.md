## (a) TL;DR

- **モデル: 据え置き** — 直近 1 週間の新規オープンウェイトで wired 90GB 以内に収まり、Flash-Next を品質で明確に上回ると裏取りできたものは無い。ただし **Ornith-1.5-122B (ornith-ai、10-16 公開、Qwen3.5-122B-A10B 系、MIT)** が自己申告で SWE-bench Verified 84.5 / Pro 76.9 / Multilingual 76.4 (同表の Flash-Next 82.8 / 43.9 / 73.0) を出しており、MLX 4bit ≈65〜70GB 常駐・mlx-serve native (`qwen3_5_moe`) で当機に載る。第三者再現がゼロで Terminal-Bench 2.1 は Flash-Next 以下 (81.2 vs 83.4) なので、**既定差し替えではなく 3 本目のエントリとして A/B する候補**に留める ((e)-2)。本命パックの後継 `ddalcu/…-iQ-MLX-4.7bpw` (常駐 75GB、code top-1 96.0%) も品質寄りの任意選択肢 ((e)-3)。
- **mlx-serve: 導入済み 26.9.3 / 最新リリース 26.10.3 (2026-10-22 公開) → 26.10.3 へ更新推奨。** 26.9.3 以降 6 リリース (26.9.4 / 26.9.5 / 26.9.6 / 26.10.1 / 26.10.2 / 26.10.3)。当機の最大の弱点「prefill 中に他の全リクエストが止まる」は 26.9.5 (prefill を 2048 刻みにして境目で decode を回す) → 26.10.1 (#568、32k prefill 中も既存ストリームが進む) → 26.10.3 (`--prefill-decode-share 0.25` 既定) で**既存ストリーム側は解消**。Flash-Next M4 Max の decode は 26.10.1 で +11% (ddalcu 実測)、26.10.2 で負荷試験 (16 agent × 50 分無失敗) と OOM 時の挙動改善。**ただし既定変更が 3 つあり YAML を同時に触る必要がある**: (1) MTP が既定 on (26.10.1) → `--no-mtp` で現状維持、(2) `reasoning_effort` 無しの thinking が **2048 トークンで打ち切られる** (26.9.5) → `filters.setParams` に `reasoning_effort?: high` を追加、(3) `--prefill-decode-share 0.25` は Flash-Next では新規リクエストの TTFT を 21〜30% 悪化させる報告 (#953、M5 Max) → まず既定で入れて dsh の体感で判断。sha256 はサンドボックスで tarball を取得して実計算し、Formula の値と一致 ((e)-1)。
- **llama-swap: 導入済み v255 / 最新 v267 (2026-10-26) → 据え置き** (v256 の「ttl 起点をロード完了時に」と v263 の `disableKeepAlives` (断続 502 対策) は有用だが現行構成で困っていない。v259 でログ API が `/api/events/logs` に分離、当機にログを読むツールは無い)。

当機の弱点に対する判定:

- **prefill 中の他リクエスト停止**: 「既にストリーム中の decode が止まる」は 26.9.5 + 26.10.1 (#568) + 26.10.3 で解消 (M5 Max 報告: 10k prefill 中のストリームの最大ギャップ 1.80 s → 0.53 s、#953 の表)。「新規リクエストが prefill 完了まで最初のトークンを待つ」は **Flash-Next では未解消** (#953: 境目 admit は qwen4_exp をスキップ)。加えて #953 は share 0.25 で**冷たい 2.5k プロンプトの TTFT 0.93 → 1.18 s、10k で 3.72 → 5.34 s** (M5 Max、26.10.3) と報告し `--prefill-decode-share 0` を回避策にしている。dsh のサブエージェント (複数ストリーム並走) では share 0.25 の方が体感が良いはずなので、まず既定で入れて観察する。PR #982 (Settings 行追加) は進行中、スケジューラ既定変更の予定は無し (自動トリアージ回答)。
- **短文 TTFT 0.4 秒遅い**: 26.10.x に直接の改善項目なし。share 0.25 はむしろ悪化方向 (上記)。
- **thinking 既定のサーバフラグ**: 依然無し (`--reasoning-budget` は上限のみ)。26.10.2 の「サーバ側既定・ロック」は温度・ペナルティ・budget だけで enable_thinking は含まれない。**26.9.5 の 2048 トークン予算が新たな落とし穴**: Hermes / opencode が `reasoning_effort` を送らないと、更新後は thinking が 2048 で閉じられる (effort ladder: minimal 1024 / low 2048 / medium 8192 / high・xhigh 無制限)。`filters.setParams` に `reasoning_effort?: high` を足す ((e)-1)。
- **Metal OOM 即死**: 26.9.5 で「同時長文は順番待ち」「GPU 上限超はロード拒否」「`--os-reserve-gib`」、26.9.6 で「収まらない長文は他 cache を追い出す」、26.10.2 で「OOM は明示エラー」。**二重常駐は依然不可** (排他スワップ維持)。

- **MTP**: 26.10.1 から既定 on。09-05 の実測では本命パックで 24k 後 −2〜−14% だったが、26.9.6 (lookup drafting、M4 Max +5〜8% @26.10.1) 以降は条件が変わっている。更新時は `--no-mtp` で現状維持 → 別途 `docs/bench/bench_ab.py` で MTP on/off を再 A/B。

`dot_config/llama-swap/config.yaml` (両エントリ共通):

- `--no-mtp`: 26.10.1 から投機ドラフトが既定 on。09-05 の実測で本命パックは 24k 後に負だったので、まず off で現状と同条件にし、後述の A/B で判断する。無検閲パックは +4〜13% だったので、A/B 後にエントリ別に外してよい。

- `--idle-evict-secs` は llama-swap の ttl と重複するので不要 (前回と同じ)。
